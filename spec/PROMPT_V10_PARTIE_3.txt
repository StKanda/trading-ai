# 76. POSITION SIZING

Créer un module dédié :

`src/risk/position_sizing.py`

Son rôle est de calculer automatiquement le nombre théorique d’actions ou de contrats à prendre pour chaque signal.

Le projet reste en PAPER ANALYSIS.

Le module calcule une taille théorique mais ne transmet jamais d’ordre à un courtier.

---

# 77. TYPE D’INSTRUMENT

Ne jamais supposer qu’une unité correspond toujours à un contrat.

Pour SPY ETF :

`instrument_type = ETF`

`contract_multiplier = 1`

La quantité correspond donc à un nombre d’actions.

Si d’autres instruments sont ajoutés plus tard :

- futures ;
- options ;
- CFD ;
- autres produits ;

leur multiplicateur doit être explicitement configuré.

Ne jamais inventer un multiplicateur.

---

# 78. RISQUE PAR TRADE

Ajouter :

`risk_per_trade_pct`

Exemples raisonnables de recherche :

- 0.10 %
- 0.25 %
- 0.50 %
- 1.00 %

Ne pas choisir automatiquement la valeur qui maximise le rendement historique.

Calcul :

`risk_budget = current_equity × risk_per_trade_pct`

Exemple :

capital :

100 000 $

risk_per_trade :

0.50 %

budget de risque :

500 $

---

# 79. RISQUE PAR UNITÉ

Calculer :

`price_risk = abs(entry_price - stop_price)`

Puis :

`unit_risk = price_risk × contract_multiplier + estimated_costs_per_unit`

Les coûts doivent inclure au minimum :

- commissions ;
- slippage d’entrée ;
- slippage de sortie.

Ensuite :

`quantity_by_risk = floor(risk_budget / unit_risk)`

---

# 80. CONTRAINTE DE LEVIER

Avec levier 1 :

`maximum_notional = current_equity`

Pour SPY :

`notional_per_unit = entry_price × contract_multiplier`

Puis :

`quantity_by_leverage = floor(maximum_notional / notional_per_unit)`

Quantité finale :

`quantity = min(quantity_by_risk, quantity_by_leverage)`

Si :

`quantity < 1`

alors :

`NO TRADE — POSITION TOO SMALL FOR RISK LIMIT`

Ne jamais arrondir automatiquement à 1 si cela dépasse le risque autorisé.

---

# 81. CAPITAL ACTUEL

Le sizing doit utiliser :

`current_equity`

et non le capital initial permanent.

Il doit donc tenir compte de :

- gains précédents ;
- pertes précédentes ;
- frais ;
- slippage ;
- drawdown.

Après une série de pertes :

la taille doit diminuer automatiquement.

Après une hausse du capital :

elle peut augmenter progressivement selon les règles définies.

---

# 82. BUDGET DE RISQUE JOURNALIER

Ajouter :

`max_daily_loss_pct`

et calculer :

`remaining_daily_risk`

Avant chaque nouvelle position.

Si le risque planifié du trade dépasse le budget quotidien restant :

`NO TRADE — DAILY RISK LIMIT`

Une fois la limite atteinte :

aucun nouveau trade pour cette séance.

---

# 83. LIMITE DE NOMBRE DE TRADES

Ajouter éventuellement :

`max_trades_per_day`

Objectif :

éviter qu’un système dégradé multiplie les entrées.

Cette valeur doit être définie avant le test final.

---

# 84. BUFFER DE RISQUE

Prévoir :

`risk_buffer_pct`

ou :

`stop_slippage_buffer`

Exemple :

risque théorique par action :

1.00 $

buffer :

10 %

risque utilisé pour le sizing :

1.10 $

Ce buffer permet un sizing plus conservateur.

---

# 85. STOP NON GARANTI

Le stop ne doit jamais être considéré comme une garantie de perte maximale.

Afficher séparément :

`PLANNED RISK`

et :

`REALIZED RISK`

Si un gap traverse le stop :

la perte réalisée peut dépasser le budget planifié.

Le backtest doit conserver cette réalité.

# 87. MÉTHODES DE SIZING

Comparer éventuellement sur RESEARCH :

- expérimental uniquement ;

# 91. LIVE WORKER

Créer un processus local séparé.

Par exemple :

`python worker.py`

ou :

`python -m src.live.worker`

Le worker live doit faire uniquement :

1. détecter une nouvelle bougie ;
2. vérifier qu’elle est complète ;
3. vérifier sa fraîcheur ;
4. calculer les features ;
5. charger le Champion ;
6. produire l’inférence ;
7. calculer le signal ;
8. calculer la taille théorique ;
9. sauvegarder le résultat ;
10. mettre à jour l’interface.

---

# 92. LE LIVE WORKER NE DOIT PAS

Le Live Worker ne doit jamais :

- entraîner ;
- optimiser ;
- modifier les paramètres ;
- changer le modèle ;
- promouvoir un Challenger ;
- modifier le risque ;
- élargir les plages de recherche ;
- passer un ordre.

Inference uniquement.

Il peut fonctionner :

# 96. SHADOW MODE

`SHADOW`

Le Shadow Mode sert à construire un historique prospectif propre.

# 99. REPLAY PARITY

vs

# 108. MARKET TIMESTAMP VS FETCHED_AT

Chaque collecte doit distinguer :

`market_timestamp`

et :

`fetched_at`

Exemple :

`market_timestamp = 10:35 ET`

`fetched_at = 10:47 ET`

Cela signifie que la bougie a été reçue 12 minutes après son instant de marché.

Ne jamais réécrire rétroactivement :

`generated_at = 10:35`

si le système n’a reçu la donnée qu’à 10:47.

# 118. HISTORICAL DATA VS OBSERVED LIVE DATA

Faire la distinction entre :

`historical_market_data`

et :

`observed_live_data`

Cette distinction est indispensable pour juger la vraie exploitabilité.

# 124. PAS DE RETRAINING AUTOMATIQUE IMMÉDIAT SUR DRIFT

1. détecter ;
2. enregistrer ;
3. éventuellement désactiver les signaux ;

Cela évite une boucle d’auto-adaptation incontrôlée.

# 128. GLOSSAIRE — PARTIE 3

Ajouter ces définitions au README.

## Position Sizing

Méthode utilisée pour déterminer combien d’actions ou contrats prendre.

## Risk Per Trade

Pourcentage du capital que le système accepte théoriquement de risquer sur un trade.

## Risk Budget

Montant monétaire correspondant au risque autorisé.

## Contract Multiplier

Valeur convertissant un mouvement de prix en impact monétaire pour une unité de l’instrument.

Pour SPY ETF :

1.

## Notional Exposure

Valeur totale de la position.

Prix × quantité.

## Planned Risk

Perte estimée jusqu’au stop, avant éventuel gap extrême.

## Realized Risk

Perte réellement observée.

Elle peut dépasser le Planned Risk.

## Risk Buffer

Marge conservatrice ajoutée au risque estimé.

## Daily Loss Limit

Perte journalière maximale autorisée avant arrêt des nouvelles entrées.

## Live Worker

Processus qui traite les nouvelles bougies et produit des signaux.

Il ne s’entraîne pas.

## Research Worker

Processus qui mène les expériences et entraîne les Challengers.

## Retraining

Nouvel entraînement d’un modèle sur les données disponibles à une date donnée.

## Shadow Mode

Mode prospectif sans ordre réel dans lequel les signaux sont enregistrés pour évaluer leur comportement futur.

## Replay

Simulation chronologique bougie par bougie du comportement du système.

## Replay Parity

Vérification que Replay, Backtest et Live produisent les mêmes calculs pour le même instant.

## Data Freshness

Mesure de l’ancienneté des données reçues.

## Data Lag

Retard entre la donnée attendue et la donnée reçue.

## Stale Data

Données trop anciennes pour être considérées comme représentatives du marché actuel.

## Market Timestamp

Heure à laquelle la bougie appartient réellement sur le marché.

## Fetched At

Heure à laquelle le système a reçu ou téléchargé la donnée.

## Provider

Source fournissant les données de marché.

## Fallback Provider

Source secondaire utilisée si la source principale est défaillante.

## Incremental Update

Téléchargement uniquement des nouvelles données ou d’une petite fenêtre récente.

## Data Revision

Modification ultérieure d’une donnée déjà publiée.

## Missing Bar

Bougie attendue mais absente.

Elle ne doit jamais être fabriquée artificiellement.

## Latency

Temps entre la clôture d’une bougie et la disponibilité effective du signal.

## Data Drift

Changement statistique des données d’entrée par rapport à la période d’entraînement.

## Model Drift

Dégradation ou changement du comportement du modèle au fil du temps.
